## 二、逐模块详细问题与优化方案

### 维度 1：架构与 Next.js 15 / React 19 规范

**发现**

- **[中] 架构宣称与实现不一致** — `AGENTS.md:47` 与 `README.md:34` 均称"纯静态 SSG 编译与 ISR 增量刷新架构"，但 `next.config.ts` 未配置 `output: 'export'`，且存在 8 个 API route handler（`app/api/**/route.ts`）。若真设 `output: 'export'`，Next.js 会因 route handler 构建失败。实际为 Node.js SSR + ISR + API Routes 混合架构。EdgeOne 需以 Node 运行时承载而非纯 CDN 静态托管，文档应消除歧义。
- **[中] 三个 admin API 路由缺 `runtime` 声明** — `app/api/admin/ask/inspect/route.ts:11`、`app/api/admin/evals/run/route.ts:6`、`app/api/admin/evals/cases/route.ts:7` 仅声明 `dynamic = "force-dynamic"`，其余四个 API 路由均显式声明 `runtime = "nodejs"`。边缘部署环境下缺失声明可能导致运行时选择歧义。
- **[低] 文档页 RSC payload 携带整棵 sectionTree** — `app/docs/[slug]/page.tsx:52` → `src/components/primitives/header.tsx:18`，`AppHeader`（`"use client"`）接收完整 `PageTreeNode[]` 递归树并序列化进每个文档页 HTML。当前 `PageTreeNode` 仅含 `id/title/href/children`（`lib/content/server.ts:8-13`）密度可控，板块树增长后可改懒加载。
- **[低] `app/opengraph-image.tsx:113` 调用 `getSiteHost()`** — 若该函数依赖环境变量/请求头，OG image 无法构建期预渲染，与文件头"构建期预渲染"注释矛盾。
- **[低] 搜索页无显式 `dynamic` 声明** — `app/search/page.tsx` 依赖 URL query 属按需 SSR，行为正确，但建议显式声明意图防止未来默认行为变更。

**合规确认**：20 个 `"use client"` 组件均使用了 hooks 或浏览器 API，标记必要，无客户端化污染；`src/` 下无任何客户端组件导入 `@supabase/supabase-js`；`app/api/ask` 与 `app/api/search` 的请求/响应结构和 `src/components/ask/provider.tsx:31-37`、`lib/ai/ask.ts:127-138` 的字段一一对齐；`loading/error/not-found/global-error` 均为纯 UI，静态兼容；`manifest.ts`/`robots.ts`/`sitemap.ts`（`revalidate = 3600`）无动态隐患。

**优化方案**
1. 修正 `AGENTS.md`/`README.md` 架构表述为"SSG + ISR + Node.js API Routes 混合架构"，或在 `next.config.ts` 注释说明部署模式。
2. 为三个 admin 路由补 `export const runtime = "nodejs"`。
3. `app/search/page.tsx` 补 `export const dynamic = "force-dynamic"`。

### 维度 3：数据层与 Supabase / Notion 发布链路

**发现**

- **[高] `.env.production` 存放疑似真实凭据** — `.env.production:1-17` 含完整 `SUPABASE_SERVICE_ROLE_KEY`、`AI_PROVIDER_API_KEY`、`NOTION_TOKEN`、`ADMIN_PASSWORD` 等值。**复核确认**：`.gitignore:24` 已排除该文件，`git log --all -- .env.production` 为空（从未入库），`.gitignore:31-32` 白名单仅放行 `.env.example`。风险从"已泄露"降级为"工作区持有真实密钥"：任何备份、同步盘、误打包都会造成泄露；EdgeOne 应改为平台侧注入密钥。若该文件曾在任何渠道流转，所有密钥应立即轮换。
- **[高] 资产下载失败降级使用 Notion 签名 URL** — `lib/publishing/assets.ts:73-91`：下载失败后 catch 块直接用 `sourceUrl`（Notion 临时签名 URL）创建 Asset，仅记 warning 不中断发布。违反内容契约"严禁直接暴露 Notion 临时签名 URL"，URL 过期后图片全部失效且难排查。
- **[高] 发布链路多处静默 catch** — `lib/publishing/job-store.ts:91,107,128,170,202,227,248,288` 共 8 处 `catch { // ignore }`：任务状态写入 Supabase 失败静默回退内存态，多实例下状态不一致；`lib/publishing/pipeline.ts:85` 回滚后 revalidate 空 catch——回滚成功但 ISR 缓存刷新失败时，线上仍展示旧版本且无告警。
- **[中] `failure_reason` 字段被滥用存运行日志** — `lib/publishing/job-store.ts:168,246,284`：将 JSON 日志数组写入 `content_versions.failure_reason`，污染列语义且与 `publication_failures` 表机制重复。
- **[中] 内容加载无分页** — `lib/content/server.ts:131-136` 对 `published_pages/published_blocks/published_assets/published_search_entries` 均 `select("*")` 一次性全量拉取，内容增长至数千 blocks 后存在超时/payload 超限风险。
- **[低] `assertServerOnly` 可被 `VITEST=true` 绕过** — `lib/integrations/server-only.ts:3`，防御深度不足但实际风险低。

**合规确认**：service role client 仅在服务端模块链使用，无任何 `'use client'` 文件触及；全项目无 `NEXT_PUBLIC_` 前缀的敏感变量；`supabase/schema.sql` 含完整 7 表 RLS（anon 只读当前版本、管理 RPC revoke/grant、已发布版本不可变触发器），与 `lib/database.types.ts` 完全对应；版本提交 `commit_published_content_version` 使用 `SELECT ... FOR UPDATE` 事务 + 指针 UPSERT，无半发布窗口；发布鉴权为 HMAC SHA-256 + timingSafeEqual 双通道；生产环境缺配置/缺版本时 fail-fast（`lib/content/server.ts:47,54`），不回退示例数据。

**优化方案**
1. 将 `.env.production` 移出仓库工作区（或清空为占位模板），密钥全部改由 EdgeOne 平台注入；确认密钥流转范围后决定是否轮换。
2. `mirrorNotionAssets` 下载失败升级为 fatal error 标记页面 failed，禁止回退签名 URL。
3. 所有空 catch 至少补 `console.error` 结构化日志；`pipeline.ts:85` revalidate 失败必须告警。
4. job-store 进度日志改用独立列或 `publication_failures` 表。
5. `loadVersionFixture` 增加分页/流式加载。

### 维度 4：AI 问答引擎与检索安全

**发现**

- **[高] `shadow` 模式未实现** — `app/api/ask/route.ts:26-38` 的 `answerMode()` 仅处理 `fixture` 与 `production`，规范第 3.1 节要求的三态（fixture/shadow/production）契约不完整，无法做上线前静默对比验证。
- **[高] 12,000 字符输入预算无硬约束** — `lib/ai/retrieve.ts:46-84` 仅限制 top-k=8 块，`lib/ai/ground.ts:25` 的 `buildAnswerPrompt` 直接 `JSON.stringify` 全部 sources 无截断；单块 `exactText` 过长时可能突破预算甚至模型上下文窗口。
- **[中] 敏感词为简单子串匹配** — `lib/ai/policy.ts:17` 用 `question.includes(term)`，"招生"类词存在误命中面；且仅检查 question，不检查检索内容本身的敏感级别。
- **[中] 超时降级无差异化文案** — `lib/ai/provider.ts:67` 超时与其余不可用统一返回 503 + `answer_temporarily_unavailable`；`src/components/ask/sheet.tsx:53` 直接显示 error 字符串，无超时友好提示。
- **[中] 日志保留周期无落地** — 规范要求的"运行日志 14 天/反馈 30 天"在代码与配置中无任何体现，完全依赖外部运维约定。
- **[低] 限流为进程内存** — `app/api/ask/route.ts:67` 的 `createMinuteRateLimiter` 用 Map 存进程内；SHA-256 哈希 IP 正确，但多实例/Serverless 冷启动下"每 IP 每分钟 10 次"实际失效。
- **[低] Citation anchor 前置校验缺失** — `lib/ai/ground.ts` 构建 citation 时直接用 `source.anchor`，`b-` 前缀校验仅在 `lib/ai/session.ts:53` 最终校验层，数据库脏数据会延迟暴露。

**合规确认**（对照规范 3-4 节逐项核对通过）：模型名经 `environment("AI_CHAT_MODEL")` 显式读取缺值即 throw（`lib/ai/ask.ts:88`）；`thinking: { type: "disabled" }` 显式关闭（`lib/ai/provider.ts:93`）；超时 8000ms（`provider.ts:50`）；仅对 429/502/503/504 重试 1 次（`provider.ts:77-81`）；输出 ≤700 tokens（`ground.ts:26`）；top-k ≤8（`retrieve.ts:51`）；`school=ncu` + 当前版本双重过滤（`retrieve.ts:65,72`、`ground.ts:22`）；未知 sourceId 的 claim 被确定性剔除（`ground.ts:35-36`）；`validateAnswerSession` 二次校验 claim-citation 引用完整性，无幻觉直达 UI 的绕过路径；系统提示约束 JSON 结构化输出且禁止生成 URL/标题/锚点（`prompt.ts:14`）；日志仅记 TelemetryEvent（requestId/latency/confidence/citationCount/mode），不含完整提问与 Key（`route.ts:18`）；Citation 角标就近显示在 claim 旁（`sheet.tsx:62-70`）；`answerSession` 经 URL + sessionStorage 恢复回答、滚动位置与草稿（`provider.tsx:82-118`）；admin inspect 有鉴权（401 拒绝）。

**优化方案**
1. 实现 shadow 分支：并行调用 fixture 与 production、比对差异后仅返回生产响应。
2. 在 `retrieveGroundingSources` 返回前累加 `exactText` 长度，超 12,000 截断尾部候选块。
3. 敏感词改边界/分词匹配并结合 `riskLevel` 联合判断。
4. ProviderError 区分 timeout 原因，前端展示差异化文案。
5. 限流迁移至 Supabase 计数行或边缘 KV，实现跨实例共享。

### 维度 5：代码健壮性、测试与部署

**发现**

- **[中] tsconfig 缺增强严格选项** — `tsconfig.json:7` 仅 `strict: true`，未开 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noImplicitOverride`、`noFallthroughCasesInSwitch`。数组/Record 越界取值静默 undefined，与 AGENTS.md 严格类型精神有差距。

- **[中] 核心服务端静默 catch** — `lib/content/server.ts:75,103,321,347`：Supabase 查询异常被 `catch { // ignore }`/`return null`/`return []` 吞掉，用户见空白页而无任何告警（与维度 3 交叉）。
- **[低] 测试代码类型逃逸** — `tests/integration/citation.test.ts:1` 含非空断言；`tests/components/search.test.tsx:27` 一处 `as unknown as`（mock 场景可接受）。
- **[低] 依赖范围宽** — `package.json` 用 `^` 范围（next `^15.3.0` 等），lockfile 锁定 next@15.5.23 / react@19.2.8 / tailwindcss@4.3.3，lockfileVersion=3，`npm ci` 可行；lock 与范围漂移时存在装到更高版本的可能。

**合规确认**：全项目 grep `: any`/`as any`/`@ts-ignore`/`@ts-expect-error`/`@ts-nocheck`/`eslint-disable` **均为零匹配**，类型纪律优秀；`.github/workflows/deploy.yml` 在 push/PR to main 上串行执行 lint→typecheck→test→build（Node 22 + npm cache），任一失败阻断合并；`@tailwindcss/oxide` 的 linux-x64-gnu/musl/arm64 平台变体已在 lockfile 锁定，EdgeOne Linux 构建可解析；`postcss.config.mjs` 为标准 v4 配置；`scripts/publish.ts`（dry-run + remote webhook + exitCode）、`scripts/eval.ts`（阈值校验 + mock 模式）、`scripts/audit-routes.ts`（HTTP 冒烟探针 + 失败退出码 1）均 CI 友好；`evals/test.json` 含 342 行结构化评测用例。

**优化方案**
1. 先开 `noUncheckedIndexedAccess` + `noFallthroughCasesInSwitch`，增量修复后再评估 `exactOptionalPropertyTypes`。
2. 为 `schema.ts`、`prompt.ts`、publishing pipeline 补单测（可借助 fixture 数据驱动）。
3. CI 中增加 `scripts/audit-routes.ts` 部署后冒烟步骤（EdgeOne preview 环境）。
4. 首次部署前手动触发一次 EdgeOne 构建，确认 oxide 原生模块加载正常。
